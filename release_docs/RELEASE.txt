CGNS version 5.0.0
=================================

INTRODUCTION
------------

This document describes the difference between CGNS 4.5.0 and
CGNS 5.0.0, and contains information on known problems in
CGNS 5.0.0.

Links to the CGNS current released source code can be found at:
<a href="https://cgns.github.io/current/download.html#supportdownload" rel="nofollow">Download</a>
User MLL documentation for the current release can be found at:
<a href="https://cgns.github.io/standard/MLL/CGNS_MLL.html#standardmll" rel="nofollow">MLL Documentation</a>
For more general information, see the CGNS home page:
<a href="http://cgns.org" rel="nofollow">CGNS.org</a>

New Features
============

    Configuration:
    -------------

    Library:
    --------
    - CPEX-0045: high-order polynomial interpolation for elements and
      solutions. Adopted by the CGNS Steering Committee on 2026-08-04
      (v3.0), with the v4 corrections amendment applied.

      SIDS additions:
        ElementInterpolation_t and SolutionInterpolation_t, both optional
          list children of Family_t, describing the mesh and solution
          interpolation bases per element type and degree.
        InterpolationType_t enumeration: ParametricLagrange,
          ParametricMonomialsPascal, CartesianMonomialsPascal,
          IsoParametric.
        ControlPointDistribution_t enumeration: GaussLobattoLegendre,
          Equidistant, GaussLegendre, WarpAndBlend. Recommended, not
          required; the stored coordinates are authoritative.
        GridLocation_t gains InterpolationPoints (value 9), required for
          all high-order FlowSolution_t nodes. Field arrays then have
          length sum(N_DOFs(e)) over the zone's cells, not one value per
          cell. NofValidGridLocation is now 10.
        FlowSolution_t gains an InterpolationDegrees IndexArray_t child
          and, for Cartesian modal interpolation, an InterpolationMetadata
          UserDefinedData_t container holding CharacteristicLength.

      New API (C, with _f Fortran bindings for each):
        cg_element_interpolation_{read,write}
        cg_element_interpolation_type_read
        cg_element_interpolation_points_{read,write}
        cg_element_interpolation_distribution_{read,write}
        cg_element_isoparametric_write
        cg_element_lagrange_interpolation_{size,count}
        cg_nelement_interpolation_read
        cg_solution_interpolation_{read,write,find}
        cg_solution_interpolation_points_{read,write}
        cg_solution_interpolation_npoints_read
        cg_solution_interpolation_distribution_{read,write}
        cg_solution_lagrange_interpolation_{size,count}
        cg_solution_monomial_size
        cg_nsolution_interpolation_read
        cg_sol_interpolation_degree_{read,write}
        cg_sol_characteristic_length_{read,write,create,partial_write}
        cg_InterpolationTypeName, cg_ControlPointDistributionName

      cgnscheck validates the new nodes and gains a -s option for strict
      CPEX-0045 conformance, which promotes the soft checks (degree
      ranges, CellCenter used with InterpolationDegrees, a stored control
      point set disagreeing with its named distribution) to errors.

      See Known Problems for interoperability with CGNS 4.x libraries.

    - Added test for Unicode (UTF-8) filepath support (CGNS-98/GitHub #494).
      The test verifies creating, reading, and modifying CGNS files with
      non-ASCII characters in directory and filenames, as well as external
      links that reference files at Unicode paths. Requires HDF5 >= 2.0.0.

    Parallel Library:
    -----------------
    - CPEX-0045 parallel support. High-order field arrays are written
      through the existing cgp_field_write / cgp_field_write_data pair;
      the interpolation descriptions live in Family_t and are written
      collectively through the serial calls with identical arguments on
      every rank.

      Added cgp_sol_characteristic_length_write_data, which writes one
      rank's element range of CharacteristicLength through the
      collective-capable MPI-IO path. The array must first be created
      collectively by cg_sol_characteristic_length_create; node creation
      is collective, so a rank that creates after another has written
      would discard that rank's range.

    - Added parallel Unicode (UTF-8) filepath test using cgp_open
      (GitHub #494). Verifies parallel coordinate I/O through paths
      containing non-ASCII characters. Requires HDF5 >= 2.0.0.
      On Windows, the test executable embeds a UTF-8 active code page
      manifest so that MPI_File_open (which uses ANSI file APIs) can
      handle UTF-8 filenames.

    Fortran Library:
    ----------------
    - BREAKING: The following Fortran parallel data APIs now take
      TYPE(C_PTR) arguments instead of Fortran arrays (CGNS 5.0):
        cgp_coord_write_data_f    / cgp_coord_read_data_f
        cgp_field_write_data_f    / cgp_field_read_data_f
        cgp_array_write_data_f    / cgp_array_read_data_f
        cgp_elements_write_data_f / cgp_elements_read_data_f

      For cgp_coord_*_data_f and cgp_field_*_data_f, the rmin, rmax,
      and data buffer arguments are all TYPE(C_PTR).
      For cgp_elements_*_data_f, only the elements buffer is TYPE(C_PTR);
      the start and end range arguments remain INTEGER(CGSIZE_T).

      Callers must add the TARGET attribute to any array passed via C_LOC,
      use C_LOC(array) to pass data, and C_NULL_PTR when a rank
      contributes no data.  Examples:

        ! Coordinate write — rmin, rmax, and data are all TYPE(C_PTR)
        INTEGER(CGSIZE_T), DIMENSION(1), TARGET :: rmin, rmax
        REAL(C_DOUBLE), ALLOCATABLE, TARGET :: coords(:)
        call cgp_coord_write_data_f(fn, B, Z, C, &
             C_LOC(rmin(1)), C_LOC(rmax(1)), C_LOC(coords(1)), ier)
        ! Rank contributes no data:
        call cgp_coord_write_data_f(fn, B, Z, C, &
             C_NULL_PTR, C_NULL_PTR, C_NULL_PTR, ier)

        ! Elements write — start/end are INTEGER, elements is TYPE(C_PTR)
        INTEGER(CGSIZE_T), ALLOCATABLE, TARGET :: elements(:)
        call cgp_elements_write_data_f(fn, B, Z, S, start, end, &
             C_LOC(elements(1)), ier)
        ! Rank contributes no data:
        call cgp_elements_write_data_f(fn, B, Z, S, start, end, &
             C_NULL_PTR, ier)

      The old convention of passing start=0/end=0 with a dummy array to
      indicate no-data is no longer supported for these six APIs.

    - BREAKING: cgp_ptlist_write_data_f, cgp_ptlist_read_data_f,
      cgp_parentelements_read_data_f, and cgp_poly_elements_write_data_f
      now accept only TYPE(C_PTR) for the data argument(s).  Callers must
      pass C_LOC(array) for data, or C_NULL_PTR when the rank contributes
      no data.  Examples:
        call cgp_parentelements_read_data_f(fn, B, Z, S, start, end, &
             C_LOC(parentelements(1)), ier)
        call cgp_parentelements_read_data_f(fn, B, Z, S, 0, 0, &
             C_NULL_PTR, ier)            ! rank has no data
        call cgp_poly_elements_write_data_f(fn, B, Z, S, start, end, &
             C_LOC(elements(1)), C_LOC(offsets(1)), ier)
        call cgp_poly_elements_write_data_f(fn, B, Z, S, 0, 0, &
             C_NULL_PTR, C_NULL_PTR, ier) ! rank has no data

    - BREAKING: cgp_parent_data_write_f now accepts only TYPE(C_PTR) for
      the parents argument.  Callers must pass C_LOC(array) for data, or
      C_NULL_PTR when the rank contributes no data.
        call cgp_parent_data_write_f(fn, B, Z, S, rmin, rmax, &
             C_LOC(parents(1)), ier)
        call cgp_parent_data_write_f(fn, B, Z, S, 0, 0, C_NULL_PTR, ier)

    - BREAKING (Windows shared library only): Fortran module procedure
      exports in the CGNS DLL have been renamed from lowercase
      (CGNS_mp_cg_xxx_f) to uppercase (CGNS_mp_CG_XXX_F) to match the
      symbol names generated by Intel Fortran on Windows with the default
      /names:uppercase option.  Any application linked against a previous
      CGNS Fortran DLL must be relinked against the new DLL.

    Migration notes — Fortran parallel data API:
    Fortran has no standard-conforming way to pass a C NULL pointer through
    an assumed-size (DIMENSION(*)) dummy argument.  The CGNS 4.x convention
    of setting start=0/end=0 with a dummy array relied on undefined
    behaviour per the Fortran standard.  In CGNS 5.0 all parallel data APIs
    accept TYPE(C_PTR) directly, eliminating the undefined behaviour.
    Required migration steps:
      1. Add TARGET to any local array passed to these routines.
      2. Replace raw array arguments with C_LOC(array(first_element)).
      3. Replace the start=0/end=0 no-data idiom with C_NULL_PTR.

    Summary of Fortran parallel API breaking changes:

      API                                     Change
      ---------------------------------------------------------------
      cgp_coord_write/read_data_f             rmin, rmax, data -> TYPE(C_PTR)
      cgp_field_write/read_data_f             rmin, rmax, data -> TYPE(C_PTR)
      cgp_array_write/read_data_f             rmin, rmax, data -> TYPE(C_PTR)
      cgp_elements_write/read_data_f          elements -> TYPE(C_PTR)
      cgp_ptlist_write/read_data_f            data -> TYPE(C_PTR)
      cgp_parentelements_read_data_f          data -> TYPE(C_PTR)
      cgp_poly_elements_write_data_f          elements, offsets -> TYPE(C_PTR)
      cgp_parent_data_write_f                 parents -> TYPE(C_PTR)

Known Problems
==============

    * A file written by the CGNS 5.0 library cannot be opened by any
      CGNS 4.x library, regardless of whether it uses CPEX-0045
      high-order features. cg_open()'s major-version guard rejects any
      file whose CGNSLibraryVersion major digit exceeds the reading
      library's, and every file this library writes is stamped 5.00.
      Placing high-order solutions in a linked file does not work around
      this: the base file itself is still stamped 5.00, so a 4.x reader
      fails on the base file before ever following the link. Producers
      serving mixed-version readers need to keep a separate CGNS 4.x
      copy of the file.

    * Parallel I/O (cgp_open) does not support Unicode (UTF-8) file
      paths on Windows. MPI_File_open passes filenames to Windows ANSI
      file APIs, which cannot handle non-ASCII characters. A workaround
      is to embed a UTF-8 active code page manifest in the application.
      Serial I/O (cg_open) with Unicode paths works correctly on Windows
      with HDF5 >= 2.0.0.

    * See https://github.com/CGNS/CGNS/issues
